# Agent Note: macOS 候选菜单按右键请求构建

Status: implemented

## Problem

#7768 的快速显隐卡顿在去掉动画后仍有独立开销：每次候选渲染都预先创建所有右键菜单、固定排位子菜单和对应菜单项。原生控制器的九候选、60 轮合成显隐样本测得中位数 23.165ms、p95 31.407ms，超过一帧预算。

## Decision

候选行只保存延迟菜单提供器，右键请求菜单时才构建，并在本次渲染内复用。提供器捕获候选身份与本次渲染 token，使用弱控制器和弱按钮引用；重画后的旧按钮不提供菜单，旧菜单操作继续走现有身份与 token 检查。普通候选与释义原地更新使用同一入口。

## Alternatives considered

跨帧缓存完整菜单可以省构建，但菜单项持有会话身份、渲染 token、词条文字和置顶状态，逐项刷新容易错用旧身份。按需创建把开销移到用户主动打开菜单时，保留现有校验，边界更小。

## Consequences

首次右键承担菜单创建成本；正常输入的候选渲染不再创建菜单树。相同九候选、60 轮显隐样本的中位数从 23.165ms 降到 11.203ms，p95 从 31.407ms 降到 22.279ms。机器负载会影响数值，样本只覆盖候选渲染与显隐，不包括引擎和应用输入连接，因此不设跨机器耗时阈值，也不把它称为整个输入链路的延迟。

原生测试使用有效的合成候选身份，检查渲染后菜单为空、首次右键创建、帧内复用及旧按钮失效。既有快捷键测试继续检查置顶、固定排位、删除和旧菜单身份校验。

检索命中的[桌面生命周期核心](../architecture/2026-10-11-desktop-lifecycle-core.md)和[展开候选网格](../feature/2026-10-12-macos-expanded-candidate-grid.md)决定身份与展示边界，不决定菜单创建时机，保留其规则；Windows、Android 的菜单笔记是其它宿主，不修改。[皮肤明暗槽位](../feature/2026-10-09-candidate-skin-light-dark-slots.md)的菜单配色仍由原来的主题解析函数在菜单请求时执行。
