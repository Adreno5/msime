# Agent Note: 双拼音节编码判定复用栈字节

Status: implemented

## Problem

`shuangpin::utils::is_accepted_syllable_code` 只需要回答一个两键编码能否解成已收录音节，却先调用返回拥有型 `String` 的 `cvt_single_sp_to_pinyin`，再把结果交给集合查询。`takes_two_keys` 在分段、双拼完整性和混输英文领先判定中反复调用它，因此每个候选键对都会为马上丢弃的解码文本申请堆存储。

已有双拼辅助码检测、快照和候选选择笔记分别约束外层输入复制与显示所有权；本片只收窄底层“编码是否可接受”的只读判定，不改变公开解码函数或那些调用方的所有权边界。

## Decision

`is_accepted_syllable_code` 先按原顺序检查零声母表，再校验两字节编码；声母和韵母表项拼入长度为 6 的栈字节数组，在栈上完成 `v` 到 `u` 的归一化并以 `&str` 查询接受集合。该函数仍遍历同一张 profile 表并保留重复韵母键的“任一解码结果被接受”语义。`cvt_single_sp_to_pinyin` 继续返回拥有型字符串，供真正需要解码文本的调用方使用。

测试先在旧实现上捕获到接受判定路径 3 次分配，再加入栈判定；另用四张内置 profile 的 26×26 编码逐项对照旧式拥有型解码结果，确认判定结果一致。受共享底层分配减少影响，双拼候选选择、双拼快照和双辅助码检测的精确分配预算同步收紧。

## Alternatives considered

- **继续调用 `cvt_single_sp_to_pinyin`**：代码最短且直接复用解码逻辑，但每个只读判断都建立并释放解码字符串，无法消除逐键热路径分配。
- **为每张 profile 预建完整的可接受编码集合**：查询可以变成一次集合查找，但要增加按自定义方案建立和缓存新状态的生命周期、内存和失效边界；本片的固定栈判定不增加常驻数据。
- **让解码函数返回借用的静态音节**：能同时改变更多调用方，但自定义 profile 和公开返回接口需要重新设计所有权，超出只读判定的必要范围。

## Consequences

双拼键对的接受判定不再为中间解码文本申请堆存储，最多使用 6 字节栈缓冲；零声母、`v` 归一化、非法编码和自定义 profile 的结果保持不变。真正需要返回拼音文本的路径仍按原接口分配，因而本片只承诺减少判定中间存储，不声称改变完整双拼查询的所有分配或端到端输入延迟。

验证覆盖双拼专项 136 项、引擎完整单元与 golden、Clippy、Rustfmt、差异检查、笔记门禁和 quick 门禁。
