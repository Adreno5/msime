# Agent Note: @ 地点补全按拼写前缀索引查询

Status: implemented

## Problem

内置地点表当前有 3302 行。`collect_place_matches` 每次按键都扫描所有地点的全拼和首字母拼写；`shenzhen` 和 `luanshi` 各只匹配一行，`zzzz` 没有命中，但仍遍历整表。此前消除了查询临时堆向量，字符串比较和全表遍历仍在按键路径上。

## Decision

地点表初始化时对两种既有拼写的编号建立排序索引，不复制字符串。查询用二分找到前缀范围，只把命中行号写入栈上位图，再按原表行号迭代，交给原有 exact/prefix、同名过滤和限额逻辑。位图大小由内置表行数在编译期决定，查询不分配临时堆存储，排序索引每进程只创建一次。

仅剩一行时，先检查源表首行是否精确匹配且不被已有名称排除；满足就沿用直接返回。这个条件下旧扫描本来只访问一行，强制走二分与位图会增加工作。其余查询使用前缀索引，不扩大快速路径的语义范围。

## Alternatives considered

- **继续全表扫描**：没有额外常驻索引，早期精确命中还可立即结束；但常见前缀、稀疏查询和未命中仍反复遍历全部拼写。
- **只按首字母分桶**：索引更小且天然保持源表顺序；但长查询仍扫描同一首字母下所有地点，无法随完整前缀收窄范围。
- **按前缀缓存全部行号列表**：查询可以直接按表序消费，避免查询时重排；但每个拼写的多个前缀都复制行号列表，常驻存储和初始化分配明显增多。
- **收集排序索引命中后用动态向量排序**：实现简单且保留源表序；但重新引入每次查询的临时堆分配，违反已有输出预算。

## Verification

- 冻结本轮之前的全表扫描，沿用已有固定数组输出。红阶段每批 1400 次混合查询的七批中位数为旧 35.665416 ms、未优化 35.605625 ms，无法满足减半预算。含首行快捷返回的最终索引实现为旧 39.011959 ms、新 2.985541 ms，约 13.1 倍局部提升；不是整输入法吞吐或端到端延迟。
- 全部完整拼写及首一、二字符前缀对照原表过滤和冻结输出；空输入、无命中、非 ASCII、空键、畸形解析均保持原行为。同一行的两种拼写只出现一次，结果按源表顺序。
- 冻结输出另对照限额 0、1、2、17、18、19，以及排除首行与多个已有名称；保留 exact/prefix 顺序、全部字段和此前公开查询分配预算。
- 冷初始化对象重建七次中位数为旧 1.530875 ms、新 2.853333 ms；计时不含 drop，不等于整进程冷启动。分配计数确认只增加一个编号向量，6604 个 `usize` 在本机 64 位上为 52832 字节。查询位图是 52 个 `u64`，共 416 字节栈空间，不申请临时堆存储。

逐项 release 基准覆盖 `a` 至 `z` 的 `limit=18` 查询和首行早期精确命中的 `limit=1`。未加快捷返回时，`bjs` 从 115.208 µs 退化到 404.833 µs（2000 次查询中位数），超过二倍计时容差，预算真实失败。修复后 `bjs` 为 117.458 → 71.292 µs、`beijingshi` 为 104.042 → 62.041 µs；单字符查询全部快于旧扫描。逐项和混合基准均通过预算，结果仅代表这些局部查询。

`cargo test -p msime-engine` 为 2077 项通过、19 项忽略，golden 31 项通过；fmt、Clippy、笔记校验及本地 quick 门禁通过。quick 包含 Linux 原生宿主 86 项测试、macOS 原生构建、Apple bridge 构建，以及 Android 和 WebAssembly 编译；缺少环境的 Windows 交叉构建、HarmonyOS ArkTS 打包按脚本跳过。两轮只读审查通过。

## Consequences

按拼写排序不能直接当候选顺序，位图必须按原行号输出。位图的容量由内置表行数导出，只用于这个嵌入表；不得用于无上限外部词库。增加一次排序与行号索引存储，须同时报告冷初始化代价和热查询收益，不能用热查询数据冒充整进程或冷启动收益。
