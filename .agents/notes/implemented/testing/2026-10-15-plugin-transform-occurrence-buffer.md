# Agent Note: 候选变换身份出现序号工作区复用

Status: implemented

## Problem

桌面 `Runtime::transform_candidates` 在旁路重放有记录的插件操作时，每次都会重新建立 `Identity::occurrences` 的座位排序、哈希计数表和结果数组。候选变换的排列工作区已经在[排列工作区复用](2026-10-15-plugin-transform-arrangement-buffer.md)中复用，但身份出现序号仍让重复重放产生短命分配。

## Decision

`PluginState` 增加 `OccurrenceBuffers`，持有座位排序数组和开放寻址表。表槽位保存当前调用的代次、候选身份哈希、一个代表座位和出现次数；每次调用只增加代次并清空逻辑内容，槽位容量跨调用保留。哈希相同时仍比较代表座位和当前快照的文本、来源、编码，所以哈希碰撞不会合并不同身份。出现序号结果数组继续按座位排列，供现有 `Identity::matches`、重排、隐藏和注释逻辑使用。

候选身份的文本和编码仍借用当前快照，插件记录的 `Identity` 仍在点名时复制完整字段。只改变出现序号的临时工作区所有权和哈希表实现，不改变重复候选的引擎次序、插件身份匹配或公开接口。

## Alternatives considered

- **只复用座位和结果 `Vec`，继续每次创建 `HashMap`**：能减少两次向量分配，但旁路重放仍申请哈希表及桶，无法消除主要的短命工作区。
- **持有带快照借用键的 `HashMap`**：`PluginState` 会跨快照保存键的借用，生命周期无法安全表达，也会把上一份快照的字符串留在缓存边界之外。
- **改用按代表座位线性查找的分组数组**：可以避免哈希表，但候选身份各不相同时复杂度会退化为平方级，不适合候选数量扩大的快照。

## Verification

先在未修改实现上加入分配回归，旁路重放的身份工作区分配为每次 9 次，测试按预期失败。实现后，`replay_of_one_annotation_has_a_bounded_identity_allocation_budget` 在 32、1,024、4,096 行候选上连续重放均为 0 次分配；排列复用回归也修正为检查旁路重放的 0 次工作区分配。24 个候选变换测试全部通过。

## Consequences

重复候选变换重放不再为座位排序、出现序号和身份计数表申请内存；候选数量增长时表按需扩容，后续小列表继续复用最近容量。开放寻址表增加了按候选文本、来源和编码计算哈希的步骤，但保留了平均常数时间的身份计数，并用完整字段比较处理碰撞。代次溢出时重置槽位标记，不影响快照数据或插件记录。
