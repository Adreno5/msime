# Agent Note: @ 查询与地点补全直接投影固定匹配行

Status: implemented

## Problem

`query_mentions` 的主机匹配最多 18 行，但仍把 exact/prefix 引用合成堆上的 `(key, text)` 向量。地点补全也创建自己的输出向量，合并时可能再次扩容，随后两层借用行才被投影为拥有字段的 `WordItem`。这让每次 `@` 按键查询为固定上限的中间行重复申请存储。

## Decision

地点查询把已收集的 prefix 行复制到 exact 数组尾部，返回固定 18 槽匹配数组和有效行数。公开查询同样用固定数组合并主机与地点借用行，最终只对有效切片创建 `Vec<WordItem>`。保留 exact 优先、每组原始顺序、用户行优先于地点、去重和权重。

## Alternatives considered

- **保留借用行向量**：所有权简单，输出长度可直接驱动最后的投影；但固定上限没有用到动态增长能力，仍为中间存储分配。
- **直接追加 `WordItem` 并最后重写权重**：减少借用行容器，保留已有私有输出接口；但主机行构造时不知道地点数量，后续追加仍可能扩容，地点的临时向量也会留下。
- **固定 18 行借用匹配再投影**：额外使用小块栈空间，但主机和静态地点的借用无需共享拥有型字段，最终存储只需按有效行数分配一次。

## Verification

公开查询的回归先在旧实现上失败：纯主机查询 9 次分配，而最终输出只需 8 次；两行主机加地点补全时 40 次，最终输出只需 37 次。新实现满足最终字段与向量的预算，无命中查询为 0 次，私有地点收集为 0 次。

冻结旧实现对照 0、1、17、18、19、1000 行主机列表，包含 exact/prefix 重排、空查询、无命中、地点补全开关和用户行去重。地点收集另对照 limit 0、1、2、17、18、19、`usize::MAX` 与已有名称过滤。混合 18 行结果少 3 次分配，最终保留的堆字节相同，瞬时逻辑堆峰值至少少一份 18 行引用元组（64 位上为 576 字节）；这不是进程 RSS 测量。

## Consequences

最终匹配行不再经过主机合并与地点输出的堆向量；公开输出仍独立拥有字符串，权重按总有效行数生成。非空结果只有最终 `WordItem` 向量和非空字段字符串的堆分配。

栈上多保留一份至多 18 行的借用匹配数组。地点 exact 数组直接承接 prefix，不再创建第三份地点行容器。所有切片都依据有效行数，未填的空槽不进入候选；prefix 复制和用户/地点合并继续受 18 行总上限约束。固定方案仅用于受小上限约束的查询，不推广到无上限输入表。
