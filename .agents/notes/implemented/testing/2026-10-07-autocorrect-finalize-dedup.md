# Agent Note: 自动纠错位置候选去重的有界结果路径

Status: implemented

## Problem

自动纠错的生产调用把 `k` 固定为 9，但每个位置在截断前可能积累数百条候选。`Search::finalize` 按入束条数选择去重方式，超过 36 行就为全部候选建立 `HashSet`，并对最后会被丢弃的尾部继续去重；稳定排序还可能为大束分配临时存储。仅取首选的公开调用也付出完整排序和去重成本。

## Decision

`Search::finalize` 只保留排序后的前 `k` 个唯一序列，取得所需数量后立即结束扫描。线性去重的选择依据是 `min(入束条数, k)` 是否超过 36：保留结果有界时，在原列表前缀中查找重复；更大的输出继续使用 `HashSet`，容量也只按结果上限预留。

`k=1` 直接扫描最低排名的候选，时间复杂度为线性。其它调用按 `(edge_count, weight, arrival)` 原地不稳定排序；`arrival` 在搜索内全局唯一，因此完整排序键无平局，与旧稳定排序的结果相同。候选的全部字段随原地压缩保留，先驱位置只有在定稿后才扩展，回溯索引沿用定稿顺序。

## Alternatives considered

- **继续按入束条数选择线性路径**：入束最多 36 行时简单且有界，但生产只取 9 个结果的大束仍会申请哈希表并处理无用尾部。
- **所有输出都线性去重**：可完全取消临时集合，但公开大 `k` 调用会出现平方级退化，因此保留输出超过 36 的哈希表回退。
- **只排序最优的 `k` 条输入**：可以缩小排序范围，但排名靠前的输入可能包含相同序列，预先截断会丢掉排名稍后的唯一结果。
- **保留稳定排序**：无需依赖排名键唯一，但 `arrival` 已提供确定性排序，临时排序缓冲没有带来额外正确性保证。

## Verification

冻结优化前的完整实现作对照，覆盖入束条数 0、1、2、9、35、36、37、128、512，唯一序列数 1、2、8、9、35、36、37、128、512，以及 `k` 为 1、2、9、35、36、37、128、513 的组合，逐字段核对排名、先驱索引、原始跨度与音节。512 条入束在 `k=1/9/36`、重复率各异时要求定稿过程零临时分配；旧实现先在同一测试失败，512 条仅取首选产生 2 次分配。

手动 release 性能对照使用同一合成输入、相同初始化与已预留的输入缓冲，只计定稿过程，不把机器相关耗时当作单测门禁。每组运行 20,000 次，本机 `k=9` 的 36、128、512 条入束分别从 18.05、91.49、996.26 ms 降至 7.98、33.37、551.99 ms；512 条入束仅取首选从 474.40 ms 降至 19.46 ms，大输出 `k=128` 从 421.50 ms 降至 259.42 ms。以上是函数局部合成对照，运行期间有其它编译任务，不能换算成整次输入延迟的下降比例。自动纠错既有测试继续覆盖 `k=1` 与 `k=9` 的首选一致性、纠错类型、成本、原始跨度和输出去重。引擎完整单元测试 1,979 项通过、15 项手动测试忽略，golden 测试 31 项通过；`cargo clippy -p msime-engine --locked --all-targets -- -D warnings`、`cargo fmt --all -- --check` 和 `pnpm run verify-notes` 均通过。`CARGO_BUILD_JOBS=6 bash scripts/verify-local.sh --quick` 通过，包含仓库契约检查、Rust 全工作区、Android 目标、两个 Wasm 目标、Android 宿主冒烟、149 项本机 Windows 原生测试、macOS 原生宿主和共享 Apple bridge 构建；Linux 因无 Docker、Windows 交叉构建因无 MinGW、HarmonyOS 因缺少工具链与已准备资源而跳过，未作这些平台的运行时验证声明。

## Consequences

常用 `k=9` 的去重最多扫描 9 个已保留序列，入束很大时也不分配临时集合；取满结果后不再处理尾部。一般排序仍是 `O(n log n)`，小输出去重最坏 `O(n * min(k, 36))`，大输出去重为预期线性，临时集合容量不超过输出上限。只有 `k=1` 取消整个排序；结果字符串和搜索其它阶段的分配不属于此处零分配预算。
