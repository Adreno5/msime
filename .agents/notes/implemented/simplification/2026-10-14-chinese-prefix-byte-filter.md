# Agent Note: 繁简词典用实际首字节排除不可能的前缀

Status: implemented

## Problem

移除端点申请和未变化输出缓冲后，`Table::longest_prefix` 仍为每个文本位置解码最多 15 字符并逐长度散列，即使词表不含该首字节。固定基线 `7a448151c8d1e89e25f72c3d305103e81f40a24d` 的规范化表 1,002 行只有 239/240 两种首字节，词组 49,794 行只有十种首字节，单字 4,012 行只有八种。词组仍含 `PN结`、`SQL注入`、`SQL注入攻击`，直接拒绝所有 ASCII 不正确。

## Decision

每张私有表用四个 `u64` 表示实际有效键的 256 种首字节。解析同一条有效词条时登记键的第一个字节；查询先看首字节是否在表内，只排除必定不匹配的字节，其余沿用原最长匹配。UTF-8 的同首字节不意味着同字符，允许假阳性但不允许假阴性。三张表仅增加 96 字节常驻字段，不增加堆申请、依赖或额外全表遍历。

## Existing decisions

按 `chinese_conversion`、`longest_prefix`、首字节、OpenCC 检索活跃笔记。两篇繁简[前缀端点](../../implemented/simplification/2026-10-14-chinese-prefix-noalloc.md)、[借用扫描](../../implemented/simplification/2026-10-14-chinese-conversion-borrow-unchanged.md)部分重叠，仍分别持有端点与输出缓冲决定；本篇只提前排除不可能的前缀。并不翻转其中对无条件跳过 ASCII 的否定。离线释义与 provider、插件、候选渲染笔记是独立消费者或规则，保留。[粤语库存首字节](../../implemented/testing/2026-10-12-cantonese-inventory-distinct-prefixes.md)提供构造时标记参考，但库存闭包和所有权不同，不能合并；拼音 key 首字节、取消首字节和插件 UTF-8 扫描均无关。不吸收或归档。

## Alternatives considered

- 改 trie：直接共享所有词长路径，可以减少中文匹配的重复散列；暂不选，需要重建初始化和内存布局，本片先消除有直接证据的必然失败查询。
- 256 字节布尔数组：无需位操作，代码直观；临时模块中做相同 CPU/输出对照，密集简转繁没有稳定优势，逆转换有小幅优势但其它样例相近。选择每表 32 字节位图，三表增加 96 字节而非 768 字节；这不是宣称位图在所有 CPU 上更快。
- 精确首字符 HashSet：能排除更多同 UTF-8 首字节的字符；不选，因为增加一次热路径散列及构造申请，且属于更大的表结构选择。

## Verification

基线源文件机械包含相同词典，在临时副本的真实 `entries.get` 调用前插入计数，不改任何生产 API。预热后只运行单个计数用例：`synthetic-001` 文本断言通过，零前缀查询预算以 117 次实际查询失败；当前副本同一预算为零并通过。计数代码与派生模块不进入生产源码。原函数仍返回同一个合成输出。

新增核心测试覆盖 `PN结`、`SQL注入` 与更长 `SQL注入攻击`，NUL/ASCII 边界、两至四字节 Unicode、同 UTF-8 首字节的不同字符、空串、无效行、空键/值和重复来源。既有独立遍历所有表键选择最大前缀的测试、扫描和 IDS 回归及真实函数分配预算保持通过。字段只保存必要条件：若文本有匹配键，首字节必然在解析该有效键时登记；首字节存在仍不能省略最长匹配。依据 Rust 官方 [str::as_bytes](https://doc.rust-lang.org/std/primitive.str.html#method.as_bytes) 的借用字节契约，不新增切片边界或 unsafe。

CPU 方法机械包含基线与当前模块，临时副本只把 HashMap 构建器统一为 `BuildHasherDefault<DefaultHasher>`，固定散列布局；生产 HashMap 及来源数据不改。对 vendored 每个有效行的键、首值与键加合成混排/繁体 IDS 后缀，两方向共 328,848 次输出对照全部相等。17 输入×两方向，预热后以本机 SDK 的 `clock_gettime_nsec_np(CLOCK_THREAD_CPUTIME_ID=16)` 测线程 CPU 时间，15 轮交替顺序，每轮 `clamp(262_144 / max(字符数, 1), 128, 16384)` 次。输入准备、初始化和对照不计时，转换与输出销毁计时。

另一个三版本受控程序测初始化与高命中样例：`Table` 大小原 40、位图 72、布尔 296 字节，三表增加字段分别为 96/768 字节。15 轮轮换三版本，每轮完整解析并销毁三表八次，线程 CPU 均次中位数为 3,316,813/3,323,490/3,327,672 ns，配对旧/位图 0.998、旧/布尔 0.996。31 轮轮换版本、每轮转换销毁 512 次的密集兼容字，s2t 为 73,813/73,965/74,248 ns，配对旧/位图 0.995；逆转换 13,737/13,513/13,332 ns，配对旧/位图 1.013。密集命中的小差异随测量改变，仍记录其可能代价，不能归纳为无回退。

固定散列布局改变了桶分布，主机负载、CPU 频率和缓存仍影响微基准；线程 CPU 排除了被调度出去的时间，但这些数值不是生产端到端延迟保证。确定收益是不存在首字节的调用不再解码候选端点或散列前缀，不设置机器间计时门禁。

## Consequences

首字节不可能命中时避免解码候选端点和散列；可能命中的调用增加一次字节读取、位操作及分支，高命中兼容字可能小幅变慢。同字节不同字符仍有原来的查询成本，逆表逐字符查询及最终输出申请不变，首次初始化仍有原表构建及新增位图登记成本。三表增加 96 字节字段，解析有效行追加固定次位操作，无额外全表扫描、堆申请、会话缓存、公共 API、依赖、文件系统/权限或 Android 资源变化。数据更新自动更新筛选集合，不能改成假设所有 ASCII 都不匹配。
